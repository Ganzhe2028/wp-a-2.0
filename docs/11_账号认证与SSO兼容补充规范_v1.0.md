# O-Week v1.1 账号认证与 SSO 兼容补充规范 v1.0

## 1. 文档状态

- 状态：本地账号发布方案已确认；OIDC/SSO 仅保留为 P1 后续设计。
- 日期：2026-08-01。
- 适用范围：账号创建、登录、Admin 账号管理、未来学校 OIDC 接入、匿名身份生成。
- 上位基线：`docs/08_v1.1_工程基线与契约.md`。

本规范解决学校 OIDC 接入时间和可用性尚不确定的问题。系统必须先以独立账号模式完成开发和交付；以后接入 OIDC 时，只迁移登录凭证，不迁移用户、作品或权限数据。

> **本次发布覆盖说明（2026-08-01）**：生产固定 `AUTH_MODE=LOCAL_ONLY`，学生使用账号编号和初始密码登录。OIDC 变量不配置，不列入本次上线验收，也不阻塞发布。若后续启动 SSO 工作，应从 `HYBRID` 方式接入，保持现有 `User`、账号编号、角色、组别和作品不变。

本规范是对原 v1.1“仅使用学校 SSO、不得使用本地密码登录”要求的明确变更。在账号认证和账号导入范围内，以本规范为准；作品、权限、匿名展示、活动设置及其他业务规则仍以 v1.1 基线为准。

## 2. 已确认的产品结论

1. 即使学校最终不提供 OIDC，网站也必须能够长期独立运行。
2. 第一阶段由 Admin 批量导入用户姓名；导入时不要求填写身份，系统统一默认创建为 `LEARNER`，之后由 Admin 在后台按需修改角色。
3. Admin 必须能在导入结果页复制单个密码、复制单行账号信息、复制全部账号信息，并一次性导出包含全部姓名、账号编号和初始密码的 CSV。
4. 初始密码不是强制到期的“临时密码”。在本地登录或混合登录模式下，只要没有被修改或重置、账号没有归档、系统没有切换为仅 OIDC，它就可以一直使用。
5. 密码明文只在创建或重置时出现一次，数据库不得保存密码明文。若导入结果页关闭后需要重新获得完整密码表，必须执行“批量重置并导出”，旧密码随即失效。
6. 导入用户并加入活动时，系统必须同时为该用户生成并持久化一个稳定、唯一的 8 位符号匿名 ID，用于“不显示姓名”功能开启后的身份展示。
7. 第二阶段可以为既有账号补充邮箱；邮箱必须通过稳定账号编号匹配既有用户，不得只根据姓名自动合并。
8. OIDC 接入后，既有 `User.id`、账号编号、角色、组别、作品和匿名 ID 均保持不变，只新增 OIDC 身份绑定。
9. Admin 也是正式用户，使用 `ADMIN` 角色和同一套账号体系。共享 `ADMIN_PASSWORD` 仅可作为迁移期实现，正式方案必须移除。
10. 系统必须内置一个受保护的初始 Admin：姓名 `SophiaXu`、邮箱 `sophiaxu@moonshotacademy.cn`。初始密码必须来自部署环境的一次性高强度 Secret，不得写入源码、测试或文档；该账号不可降级、不可归档、不可删除，但必须支持有审计且会撤销全部会话的单个密码重置。

## 3. 阶段一：独立账号模式

### 3.1 首个 Admin

首个 Admin 由受控的数据库 seed 或幂等启动初始化流程创建，不能通过公开注册页面创建。固定资料如下：

| 字段 | 固定值 |
|---|---|
| `displayName` | `SophiaXu` |
| `email` | `sophiaxu@moonshotacademy.cn` |
| `role` | `ADMIN` |
| 初始本地密码 | 部署环境 `PROTECTED_ADMIN_INITIAL_PASSWORD`；16–128 个字符，首次安全初始化后移除 |

首个 Admin 创建后，可在 Admin 后台创建其他 Admin 或批量导入普通用户，但系统必须保证：

- 初始化过程幂等，同一活动中不得重复创建 SophiaXu；
- SophiaXu 不参与批量重置；允许 Admin 通过单个重置显式轮换密码，成功后立即撤销该账号全部会话并写入审计；
- SophiaXu 的姓名、邮箱和角色均不可修改，账号不可归档或删除；
- 最后一个有效 Admin 不可被降级或归档；
- 创建、改角色、归档和重置密码均写入审计日志；
- 不提供公开自助注册入口。

`PROTECTED_ADMIN_INITIAL_PASSWORD` 不得使用示例值、历史固定值或与其他环境复用；现有部署首次运行安全版本时必须用该 Secret 自动替换旧凭据并撤销旧会话。初始化成功后移除环境变量，后续轮换只通过有确认、幂等和审计保护的单个重置完成。登录限流、服务端会话、CSRF/Origin 校验和审计要求仍必须完整执行。

### 3.2 用户批量导入

第一阶段导入 CSV 至少支持以下字段：

| 字段 | 必填 | 说明 |
|---|---:|---|
| `displayName` | 是 | 用户真实姓名；可以是中文名、英文名或学校确认的显示名 |
| `role` | 否 | 省略时固定为 `LEARNER`；如导入文件带有该列，也只接受 `LEARNER`，避免批量导入意外创建高权限账号 |
| `group` | 否 | 所属组别的稳定标识或经过验证的组名，可由 Admin 导入后补充 |
| `email` | 否 | 第一阶段可以为空；有值时先保存为待验证邮箱，不等于已绑定 OIDC |

每次导入必须绑定到明确的活动 `eventId`。服务端在一个事务内完成：

1. 校验整份 CSV；
2. 创建或明确匹配正式 `User`；
3. 生成全局唯一、不可变的 `accountCode`；
4. 生成高强度随机初始密码并只保存哈希；
5. 建立活动关系，并将角色默认设置为 `LEARNER`；有组别时建立组别关系；
6. 为该活动生成并保存 8 位匿名 ID；
7. 写入 Admin 审计日志；
8. 返回一次性账号凭据清单。

批量导入采用全有或全无事务。任何一行格式错误、账号冲突、指定组别不存在或匿名 ID 冲突重试失败时，整批不得产生部分账号。

Admin 可在账号创建后通过 Account Drawer 或批量操作把普通账号修改为 `SENIOR` 或 `ADMIN`。角色修改必须由服务端校验、使用乐观锁并写入审计日志；不能依赖前端隐藏选项。

### 3.3 账号编号

`accountCode` 是稳定账号标识，并承担以下用途：

- 第一阶段登录用户名；
- Admin 搜索、重置和导出账号的稳定键；
- 第二阶段邮箱补录时的匹配键；
- OIDC 迁移前后核对同一用户的依据。

账号编号不得使用姓名派生，也不得因姓名、邮箱、角色、组别或登录方式变化而改变。数据库必须设置唯一约束。

具体编号前缀、长度和字符集可由实现确定，但一旦进入生产环境即视为稳定公共契约，不得在没有迁移方案的情况下修改。

### 3.4 初始密码

- 普通账号使用 Node.js `node:crypto` 的密码学安全随机源生成，至少 16 位；受保护初始 Admin 使用部署环境提供的唯一 16–128 位高强度 Secret。
- 字符集应排除视觉上容易混淆的字符，方便人工分发和输入。
- 使用 `scrypt` 加盐哈希，数据库只存 `salt:hash` 格式或等价的版本化哈希格式。
- 登录比较使用恒定时间比较。
- 初始密码默认不自动过期，用户可以长期使用。
- 用户改密、Admin 重置、账号归档或切换为 `OIDC_ONLY` 后，旧密码立即失效；受保护初始 Admin 只开放单个重置，不参与批量重置。
- Admin 重置密码时，现存登录会话必须全部失效。

产品界面和文档统一称为“初始密码”，避免“临时密码”让用户误以为系统会自动过期。

### 3.5 一次性凭据展示与 CSV

导入成功页必须显示本次创建的全部账号，并提供：

- 复制单个初始密码；
- 复制单行“姓名 + 账号编号 + 初始密码”；
- 复制本批全部凭据；
- 下载本批凭据 CSV；
- 明确提示“关闭或刷新后无法再次查看这些密码”。

最低 CSV 格式：

```csv
displayName,accountCode,initialPassword
张三,OWK-7K3M2P,example-password
```

可附加 `role`、`group`、`email` 等管理字段，但不得缺少 `displayName`、`accountCode` 和 `initialPassword`。

明文密码只能存在于：

1. 创建或重置请求的服务端短生命周期内存；
2. 该次响应；
3. Admin 当前页面内存；
4. Admin 主动下载的 CSV 文件。

服务器不得把明文密码写入数据库、日志、审计记录、缓存或可再次下载的文件。Admin 页面刷新后不能从服务器“查看原密码”。如需重新分发，Admin 必须执行单个或批量重置，并导出新密码；旧密码立即失效。

## 4. 8 位符号匿名 ID

### 4.1 生成时机

当用户被导入并加入某个活动时，系统必须为 `(eventId, userId)` 生成一条 `EventAnonymousId`。如果同一正式用户参加多个活动，每个活动使用不同的匿名 ID。

如果账号先创建、稍后才加入活动，则在建立活动成员关系的同一事务中生成匿名 ID，不得生成无活动归属的匿名 ID。

### 4.2 格式

- 固定长度：8 位；
- 允许字符集：`! @ # $ % & * + ? =`；
- 不得包含字母、数字、空格、姓名片段或 Emoji；
- 示例仅用于说明格式：`@%+!?$&*`。

每一位从允许字符集中使用密码学安全随机源独立抽取。不得使用 `Math.random()`。

### 4.3 唯一性与稳定性

- 数据库对 `(eventId, anonymousId)` 设置唯一约束；
- 数据库对 `(eventId, userId)` 设置唯一约束；
- 碰撞时重新生成并重试；达到有限重试上限后，整批导入失败并回滚；
- 生成成功后持久化，刷新页面、重新登录、更换设备、修改姓名或切换登录方式均不得改变；
- 不得在每次请求时重新随机生成；
- 普通用户不可自行修改匿名 ID；如确需 Admin 重置，必须是显式高风险操作并写审计日志。

### 4.4 不显示姓名时的展示规则

当活动设置 `show_name=false` 时，所有学生可见页面和公共响应使用匿名 ID 代替真实姓名。必须在查询和序列化阶段移除真实姓名，而不是只在前端用 CSS 隐藏。

真实姓名不得出现在：

- 作品详情和浏览列表；
- 搜索结果、筛选项和排序键；
- 页面标题、Meta、分享预览和图片替代文本；
- ARIA 标签和其他无障碍文本；
- 客户端 JSON、预加载数据和错误信息；
- 可由普通用户访问的接口响应。

Admin 在经过权限校验的后台仍可查看真实姓名和匿名 ID 的对应关系。该读取属于敏感操作，应有审计记录或至少可审计的请求记录。

## 5. 建议领域模型

正式实现不得继续向原型 `Person` 堆叠认证字段。建议使用以下职责分离：

| 模型 | 核心字段 | 职责 |
|---|---|---|
| `User` | `id`, `accountCode`, `displayName`, `email?`, `role`, `status` | 稳定用户身份和业务权限 |
| `LocalCredential` | `userId`, `passwordHash`, `passwordChangedAt` | 本地密码凭证 |
| `OidcIdentity` | `userId`, `issuer`, `subject`, `boundAt` | 一个或多个外部身份绑定 |
| `Session` | `userId`, `expiresAt`, `revokedAt` | 可撤销的服务端会话 |
| `EventAnonymousId` | `eventId`, `userId`, `anonymousId` | 每活动稳定匿名身份 |
| `AdminAuditLog` | `actorUserId`, `action`, `targetDigest`, `createdAt` | 敏感管理操作审计 |

作品、提交、收藏、公开作品 ID、角色和组别关联必须指向 `User.id`，不得指向姓名、邮箱、账号编号或某种登录凭证。这样登录方式变化不会导致作品归属变化。

如果现有代码暂时把 `issuer` 和 `externalSubject` 直接放在 `User` 上，迁移到多个身份提供方时应采用增加 `OidcIdentity` 表的迁移，不得重建用户。

## 6. 三种认证模式

部署配置提供明确的认证模式，例如：

```env
AUTH_MODE=local
```

| 模式 | 本地账号密码 | 学校 OIDC | 适用阶段 |
|---|---:|---:|---|
| `local` / `LOCAL_ONLY` | 开启 | 关闭 | 当前独立开发和无 OIDC 的长期运行 |
| `hybrid` / `HYBRID` | 开启 | 开启 | OIDC 灰度、绑定验证和回退期 |
| `oidc` / `OIDC_ONLY` | 关闭 | 开启 | 学校 SSO 稳定后的可选最终状态 |

模式切换建议路径：

```text
LOCAL_ONLY -> HYBRID -> OIDC_ONLY
```

`OIDC_ONLY` 不是强制终点。如果学校不提供 OIDC，系统可以永久保持 `LOCAL_ONLY`。如果 OIDC 暂时故障，可按受控变更流程从 `OIDC_ONLY` 回退至 `HYBRID`，无需迁移用户和作品。

切换到 `OIDC_ONLY` 时不应立即删除本地密码哈希；先禁用本地登录并保留一段回退期。是否在回退期结束后清除本地凭证，由正式运维策略决定。

## 7. 阶段二：邮箱补录与账号匹配

接入 OIDC 前，由 Admin 为既有用户批量补充学校邮箱。推荐 CSV：

```csv
accountCode,displayName,email
OWK-7K3M2P,张三,student@example.edu
```

匹配规则：

1. `accountCode` 是唯一权威匹配键；
2. `displayName` 只用于 Admin 人工核对，不参与自动合并；
3. 邮箱必须规范化后校验唯一性；
4. 同一个邮箱匹配多个用户、一个用户出现多个邮箱或账号编号不存在时，该行进入冲突队列；
5. 只有姓名、没有账号编号的 CSV 可以生成候选匹配报告，但不得自动写入；
6. 邮箱补录不得改变 `User.id`、账号编号、作品归属、匿名 ID、角色或组别；
7. 补录操作及冲突处理必须写 Admin 审计日志。

## 8. 阶段三：OIDC 绑定

### 8.1 首次登录绑定

OIDC 回调必须同时满足：

- `issuer` 位于配置的允许列表；
- Token 的签名、受众、nonce、时效验证通过；
- 身份提供方明确返回 `email_verified=true`；
- 邮箱恰好匹配一个 `ACTIVE` 且已预置的用户；
- 该用户没有绑定到另一个冲突的 `(issuer, subject)`；
- 同一 `(issuer, subject)` 没有绑定其他用户。

满足条件后，在事务中创建 `OidcIdentity`，写入审计日志并建立会话。任一条件不满足时必须 fail closed，交由 Admin 处理，不得自动新建用户或按相似姓名猜测。

如果学校可以提前提供稳定 `subject`，应优先由 Admin 按 `accountCode + issuer + subject` 预绑定，这比首次登录按邮箱绑定更安全。

### 8.2 后续登录

首次绑定完成后，后续 OIDC 登录只通过 `(issuer, subject)` 定位用户。邮箱和姓名的后续变化不得创建新用户，也不得改变作品归属。

### 8.3 账号合并限制

系统不得自动合并两个已产生作品或登录记录的用户。发现重复账号时，必须由 Admin 通过专门的冲突处理流程确认；合并前要展示受影响的作品、角色、组别、匿名 ID 和会话，并完整审计。

## 9. 登录与安全要求

- 学生和 Admin 使用同一身份模型，但所有权限仍由服务端角色校验；前端隐藏按钮不构成授权。
- 登录接口同时按 IP 和账号编号限流；生产环境使用跨实例持久化限流，不依赖单进程内存。
- 会话由服务端设置 `HttpOnly`、`Secure`、`SameSite=Lax` Cookie，不使用 `localStorage` 或脚本设置 Cookie。
- 会话应可撤销；密码修改、密码重置、账号归档和关键角色变化后撤销相关会话。
- 写操作需要 CSRF 或严格 Origin 校验。
- 缺失认证密钥、OIDC 配置或系统设置时必须 fail closed。
- 日志和审计记录不得包含明文密码、Token、Cookie、姓名、邮箱或作品内容；目标用户使用不可逆摘要标记。
- 下载凭据 CSV 属于敏感操作：仅 Admin 可执行，响应禁止共享缓存，并建议添加 `Cache-Control: no-store`。

## 10. Admin 后台能力

正式 Admin 后台至少包含：

1. 批量导入用户并一次性导出初始凭据；
2. 复制单个密码、单行凭据和本批全部凭据；
3. 按账号编号、姓名、角色、组别和状态查询用户；
4. 单个重置密码；
5. 批量重置并一次性导出新密码；
6. 批量补录邮箱并处理冲突；
7. 查看 OIDC 绑定状态，不展示 Token；
8. 启用、归档、改角色和改组别；
9. 查看用户对应的活动匿名 ID；
10. 查看关键操作审计记录。

密码重置确认界面必须明确提示“旧密码和现有会话将立即失效”。批量重置是高风险操作，需要二次确认并显示影响账号数量。

所有重置、批量角色修改、归档和删除操作必须自动排除固定初始 Admin，并在界面中清楚标记该账号为“系统初始 Admin”。

## 11. 与当前原型的迁移边界

当前发布不迁移旧 `Person` 数据。它及其关联记录仅作为历史备份；旧登录、旧学生资料和旧管理入口均不属于正式运行流程。开发时遵守以下边界：

- 新能力围绕正式 `User` 及独立凭证模型建设；
- 不继续把邮箱、OIDC 绑定、匿名 ID 或更多认证状态堆入 `Person`；
- 本次发布不建立 `Person` 到 `User` 的映射，也不兼容旧登录；
- 不得仅按姓名、邮箱、账号编号或其他旧字段猜测合并；
- 所有正式账号和作品只归属于正式 `User.id`；
- 新增或修改 API 时先更新 `lib/contracts/**`，再实现服务端和 UI；
- 将来如需处理旧数据，必须作为独立、经确认的工作项，不得自行修改数据库迁移。

## 12. 验收标准

### 12.1 独立账号

- 导入 N 个合法用户后，事务内创建恰好 N 个账号和 N 条活动匿名 ID；
- 只提供姓名的合法导入会把所有新账号创建为 `LEARNER`；
- Admin 可在导入后把普通账号修改为 `SENIOR` 或 `ADMIN`，并产生审计记录；
- 返回的凭据 CSV 恰好包含 N 行，并包含姓名、账号编号和有效初始密码；
- 每个账号编号全局唯一，且修改姓名、邮箱和登录方式后保持不变；
- Admin 可以复制单个密码、单行和全部凭据；
- 页面刷新后服务端无法再次返回原始密码；
- 在 `LOCAL_ONLY` 和 `HYBRID` 下，未被修改或重置的初始密码长期有效；
- 在 `OIDC_ONLY` 下，本地密码登录被服务端拒绝。
- 受保护初始 Admin 始终保持姓名 `SophiaXu`、邮箱 `sophiaxu@moonshotacademy.cn` 和角色 `ADMIN`；降级、归档与删除被拒绝，单个密码重置成功后旧密码和全部旧会话立即失效。

### 12.2 匿名 ID

- 匿名 ID 恰好 8 位；
- 每一位都属于 `!@#$%&*+?=`；
- 同一活动内唯一；
- 同一用户在同一活动内稳定；
- 同一用户参加不同活动时使用不同匿名 ID；
- `show_name=false` 时，学生可访问的 HTML、JSON、Meta 和无障碍文本中均不存在真实姓名及可还原身份字段。

### 12.3 密码与会话

- 数据库、应用日志、审计记录和缓存中不存在密码明文；
- 重置后旧密码立即失败；
- 重置、改密、归档和关键角色变化后旧会话失效；
- 一次性凭据响应和 CSV 下载均不可被共享缓存。

### 12.4 邮箱与 OIDC

- 邮箱批量补录通过账号编号匹配，不按姓名自动合并；
- 冲突行不产生部分写入或错误绑定；
- 首次 OIDC 绑定只接受已验证邮箱和允许的 issuer；
- 绑定前后 `User.id`、账号编号、作品、角色、组别和匿名 ID 不变；
- 后续 OIDC 登录只通过 `(issuer, subject)` 定位用户；
- 学校 OIDC 永远不可用时，系统仍可在 `LOCAL_ONLY` 下完整运行。

## 13. 非目标

本补充规范不新增以下功能：

- 学生自助注册；
- 学生自助找回密码；
- 通过姓名自动合并账号；
- 保存或恢复旧密码明文；
- 允许普通用户修改匿名 ID；
- 将账号编号、邮箱或匿名 ID 作为作品数据库主键；
- 因接入 OIDC 而重建用户或迁移作品所有权。

## 14. 实施顺序

1. 固化 `User`、本地凭证、会话、活动匿名 ID 和审计契约；
2. 完成数据库迁移和固定初始 Admin 的幂等 seed；本次发布不读取、不写入或映射旧 `Person` 及其关联记录；
3. 完成默认 `LEARNER` 的 Admin 姓名批量导入、一次性凭据展示与 CSV；
4. 完成本地登录、会话撤销、限流和 Admin 角色授权；
5. 完成匿名模式的数据级去标识化测试；
6. 上线并长期支持 `LOCAL_ONLY`；
7. 获得学校 OIDC 参数后，再开发邮箱补录、冲突处理和身份绑定；
8. 经过灰度验证后由 `HYBRID` 决定是否进入 `OIDC_ONLY`。

任何阶段都不得为了等待 OIDC 阻塞独立账号模式的开发和交付。
